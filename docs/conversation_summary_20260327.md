# 대화 정리

이 문서는 최근 대화에서 정리된 핵심 결론을 한 장으로 묶은 메모입니다.

## 1. MSDS 검증 결론

- 공개 MSDS 텍스트본은 구조화 입력으로 충분히 사용할 수 있다.
- HTML과 TXT 둘 다 검증이 가능했고, 같은 물질 기준으로 맞춰서 확인하는 것이 중요하다.
- 샘플 혼입이 있으면 파일명만 믿으면 안 되므로, 본문 제품명과 CAS No.까지 같이 확인해야 한다.
- 현재는 `도데칸니트릴(CAS No. 2437-25-4)`과 `4-브로모톨루엔(CAS No. 106-38-7)`을 각각 별도 배치로 검증했다.

## 2. 파일명과 폴더 규칙

- 파일명은 `msds_{product_slug}_{cas_no}.{ext}` 형식으로 통일한다.
- 같은 CAS No.의 HTML/TXT/PDF는 같은 폴더에 둔다.
- 폴더는 CAS마다 나누지 않고, 검증 목적이 다를 때만 분리한다.
- 검색은 `CAS No.` 우선, 제품명은 보조 검색어로 쓴다.

## 3. 신뢰성 기준

- 파일명, 본문 제품명, CAS No.가 일치해야 한다.
- HTML/TXT/PDF가 같은 물질인지 반드시 확인한다.
- 이상이 있으면 배치 리포트는 참고용으로만 보고, 신뢰 데이터로 쓰지 않는다.
- 사람용 리포트와 디버그용 JSON을 분리해서 본다.

## 4. 제조 문서 에이전트 방향

- 1차 타깃은 시험성적서 / COA다.
- 그 다음은 사양서 / 스펙 비교다.
- 규칙 기반 코어를 먼저 만들고, 로컬 LLM은 설명/초안 보조로 붙인다.
- 클라우드 LLM은 복잡한 예외 케이스에서만 선택적으로 쓴다.
- 정부 문서 / 입찰 서류는 별도 트랙으로 보는 게 깔끔하다.

## 5. 인프라와 모델 구분

- Oracle Cloud / AWS / GCP는 인프라다.
- OpenAI / 로컬 LLM / 규칙 기반은 모델 옵션이다.
- 클라우드 서버와 클라우드 LLM은 같은 말이 아니다.
- 기업에는 인프라 옵션과 모델 옵션을 분리해서 제시하는 편이 이해가 쉽다.

## 6. 실무적으로 남긴 결론

- 처음부터 거대한 자동화보다 작은 구조화 실험이 더 중요하다.
- 문서 파싱, 정규화, 이상탐지는 규칙 기반이 강하다.
- 로컬 LLM은 해설, 초안, 예외 설명에 붙이는 것이 현실적이다.
- 클라우드는 기본이 아니라 선택적 보강 옵션으로 두는 게 낫다.

## 7. 한 줄 요약

MSDS 검증으로 구조화 파이프라인의 신뢰성을 확인했고, 다음 단계는 시험성적서 / COA 중심의 제조 문서 에이전트를 규칙 기반 코어 + 로컬 LLM 보조 구조로 만드는 것이다.
